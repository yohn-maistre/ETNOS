# Commons, activity and encrypted DM checkpoint

1 November 2026 (Asia/Bangkok). This is an invited-user **experimental preview**, not full PieFed parity, a production institutional vault or a qualified secure messenger.

## Delivered behavior

- Local Groups have public/hidden profiles, separately protected membership, stewards and forum Spaces. Creating/belonging to a Group grants no private forum admission. Hidden spaces and rosters are omitted from unauthorized views. AT Groups/Spaces interoperation remains disabled; the local authority does not depend on that upstream proposal.
- Curated public Contexts represent places, regions, topics and languages. Human authors/stewards attach public contributions; private discussions cannot be indexed this way. These are discovery/collection contexts, not personal ethnic affiliation or institutional membership claims.
- Institutional/governed-community PublicWork requires a public sponsor requested by its steward and admitted by the node steward. Ordinary conversation never becomes work automatically. Adopting someone else's post requires current, exact-text author consent. Agent work grants are separate from posting grants, sponsor-bound, expiring/revocable and budgeted. Human review binds result digest and current work revision and creates a distinct public result identifier.
- Public Wiki agents can submit restricted proposals under a separate editorial mandate issued by their registered operator who currently governs that forum. Posting alone grants no editorial right. Only human stewards accept the exact current-base/digest proposal. Useful model execution and production agent service credentials are not connected by this policy work.
- A private activity inbox covers replies, Wiki review/decisions, admission requests/decisions and generic DM notices. Current access/roles are checked before projection, including unread counts. Only read marks are stored; notification text is not a stale content snapshot. The newest 100 eligible events form the inbox window. No mentions, email/web push, background delivery service or subscription engine is claimed. Actual workerd's compound SELECT limit required two bounded projections merged in stable order.
- Honai's connected app uses shadcn-svelte components throughout the shell, dialogs, login-01 adaptation, forms, cards, tabs, menus, mobile sheet and messages. Lucide is the icon set. Aksara/Abstraksi palette presets and validated custom accents persist as presentation preferences; contrast roles adapt to light/dark surfaces. Taste v2.1.5 app patterns informed the audit. No imaginary activity was seeded in public storage.

## First forum DM slice

Only enrolled **humans** with an explicitly activated messaging device can participate. One browser/device per account; one-to-one text; invitation/acceptance before sending; inbox, blocking/closing, generic activity notices and a comparison security code. Agents, groups, media, interoperability, read receipts exposed to peers, automatic recovery and device replacement are not enabled. Opening a DM does not grant community or institutional authority.

The client uses pinned **ts-mls 1.6.4** with the standard P-256/AES128GCM/SHA256 MLS ciphersuite. This library explicitly has no formal security audit. Its current main-branch documentation differs from the pinned API; implementation and tests use the installed version's actual types. The crypto adapter uses an application AuthenticationService that pins each participant's actor/device/signing key, validates the exact two-member group and group ID, rejects unsupported membership changes and validates encrypted payload identity. It does not use the library's accept-all credential service. The current UI does not periodically advance MLS membership epochs: no post-compromise recovery or post-quantum guarantee is claimed.

Client session/ratchet state and local readable history live in **passphrase-encrypted IndexedDB**, not server storage or localStorage. PBKDF2-SHA256 (600,000 iterations, random salt) derives a non-extractable AES-256-GCM vault key, with fresh IVs and account/origin/version-bound AAD. The phrase never enters API requests. The active page holds an exclusive Web Lock, locks when hidden/unmounted and after ten minutes without DM operations, and clears rendered plaintext. This does not defeat compromised devices/extensions or malicious JavaScript served by the host. Losing the phrase or browser data loses access; there is deliberately no silent reset that replaces someone's established messaging key.

The server stores public device keys, single-use public KeyPackages, encrypted Welcome/messages and private routing/read/block metadata. It cannot decrypt those envelopes using the stored server-side state. Hosting operators can see correspondents, timing and sizes, and can attack availability or initial key discovery. Initial identity/key trust still depends on the authenticated service; manually compare the security code using a separate trusted channel. There is no independent key-transparency service or external security review. The UI warns against sensitive use during setup.

Recipient KeyPackages are claimed atomically and never returned to the unused pool. Registration, initialization and message delivery tolerate exact retries; changed payloads under the same identifier conflict. The client persists its new ratchet state and exact ciphertext intent **before** sending. A failed storage write locks the vault and prevents an outward send. Ambiguous delivery retries use the same ciphertext/client ID. No native plaintext fallback exists. The API bounds ciphertext sizes, restricts participants, rejects device mismatches and prevents new sends/requests after a block. Enrollment remains invited; request/send quotas and a maximum 100 conversations/1,000 envelopes per conversation are initial limits, not comprehensive anti-abuse qualification. A sender's first version is server ordered; peer read markers never appear in the other participant's view.

**Origin changes now need a client-key migration plan.** Adding etnos.space to the existing Worker preserves server storage, but browser IndexedDB and its AAD are origin-bound. Do not move activated DM users to a new origin without a qualified transfer/rekey path or continued access through the old origin. No encrypted backup import/device cloning is exposed in this first slice.

## Evidence and remaining work

Node policy tests and actual-workerd contracts exercise isolation, private projections, revocation/expiry, grants, exact-base/digest review, atomic migrations/nested rollback, idempotent DM operations, generic activity, blocking and no DM outbox export. Native crypto tests use real MLS messages in both directions, serialization, replay rejection and changed-key/group rejection.

Cloud Chromium tests run the actual built UI with every auth/API request intercepted into isolated in-memory ETNOS instances. They exercise posting/replies/votes/bookmarks/Wiki, Group/Space/sponsor/work/result/context flows, theme/accent persistence, mobile sheet behavior, and two independent browser profiles exchanging real encrypted messages. The DM test verifies no plaintext/passphrase in captured API requests/database envelopes, matching comparison codes, encrypted local persistence, wrong-phrase rejection and blocking. These fixtures never provision a deployed node and make zero real public writes. They do not prove real-provider OAuth completion, physical-phone performance or comprehensive security.

Before sensitive DM use: independent security review, key transparency/verification UX, device/recovery/succession design, forward-update/rekey behavior, origin migration, backup/restore, mobile performance and accessibility testing, operational retention/deletion and abuse/unblock/reporting policy. Existing plaintext on a recipient's device cannot be revoked by blocking. The separate [messaging research](../research/2026-10-31-private-messaging.md) records Germ/Matrix/Signal options without implementing interoperability.

Other launch gates remain owned production Lexicons/live AT qualification, PDS/account hosting, ordinary post lifecycle/media/moderation, operational backups/resource limits and Aksara/A2A/Iroh integration. Hosted AT login does not itself create a PDS account or migrate giyaibo.bsky.social.
