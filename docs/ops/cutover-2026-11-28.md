# Cutover to the new Cloudflare account (plan, 28 November 2026)

This page is the plan for moving etnos.space to the owner's new Cloudflare account. The general runbook is [fresh-cloudflare-migration.md](fresh-cloudflare-migration.md); this page records the facts that apply to us and the order of the steps.

## Facts checked on 28 November

- `etnos.space` is registered at **Namecheap**. Its nameservers are Cloudflare's (`cartman` and `molly`), which serve the zone in the old account. The domain does not need a registrar transfer. It moves by adding the zone to the new account and changing the two nameservers at Namecheap ([Cloudflare: move a domain between accounts](https://developers.cloudflare.com/fundamentals/manage-domains/move-domain/)).
- The new account gets its own nameserver pair, which can differ from the old pair. While the zone is *Pending* in the new account, it cannot proxy traffic. When Namecheap points at the new pair, the zone turns *Active* there, and the old zone shows *Moved Away* and is deleted after 7 days.
- DNSSEC must be off at Namecheap before the move.
- Cloudflare does not copy settings between accounts. The DNS records are exported from the old zone and imported into the new one, and certificates are issued again.
- The identity host holds 2 accounts: `uji-1.etnos.space` (test) and `giyaibo.etnos.space` (the owner's). Both DID documents name `etnos-identity-host.giyaibo.workers.dev`, which belongs to the old account.
- The node moves with its backup: Studio, *Pengaturan*, then the download, then `POST /v1/ops/restore` on the new Worker (runbook §1b).

## Order

1. **Finish and check everything on the old account first** (owner decision, 28 November).
2. **Move the identity host to `akun.etnos.space` on the old account** (runbook §6). This step repoints both DID documents to a name that we control, while the old host still holds the keys. After it, the workers.dev name no longer matters.
3. **Decide how the two host accounts move.** This is open. The key-encryption key on the old host was made by the deploy workflow, so its value is not known outside the Worker. Three options follow, and the choice is made before the cutover day.
   - *Standard AT account migration.* The new host creates each account with its existing DID, imports the repository and blobs, and the old host signs the PLC update. This needs the host to accept incoming migrations; check the code first.
   - *Rotation with the escrow key.* The owner's offline escrow key signs a PLC update that points each DID at new keys on the new host. The repository comes from the CAR backup.
   - *A fresh test account.* `uji-1` is a test account and can be made again.
4. **Cutover day, in one window of about an hour**, announced to the alpha group:
   - Set the GitHub secrets `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` to the new account (the owner does this in GitHub settings, never in chat). Set the repository secrets `ETNOS_LINK_KEY`, `ETNOS_VAPID_PUBLIC_KEY` and `ETNOS_VAPID_PRIVATE_KEY` if we want them stable.
   - Create `etnos-node-backups` and `etnos-identity-blobs` in the new account and run the deploy workflow. Both Workers then answer on the new workers.dev name.
   - Download the node backup from the old Studio, and restore it into the new node.
   - Move the host accounts as decided in step 3.
   - Add `etnos.space` to the new account, import the exported DNS records, turn DNSSEC off at Namecheap, and change the nameservers there.
   - When the zone is *Active*, the deploy workflow attaches `etnos.space`, `*.etnos.space/*` and `akun.etnos.space/*`.
   - Run runbook §5 checks, then sign in as the operator and as a test account.
5. **Writes during the window are not carried over.** Some readers reach the old account until their resolvers see the new nameservers. The window is announced so that nobody posts during it.

## What the owner provides

- The new account ID and API token, as GitHub secrets on the cutover day.
- Namecheap access for the nameserver change and DNSSEC.
- The escrow key, if step 3 uses it.
