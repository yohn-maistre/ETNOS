# Cutover to the new Cloudflare account (plan, 28 November 2026)

This page is the plan for moving etnos.space to the owner's new Cloudflare account. The general runbook is [fresh-cloudflare-migration.md](fresh-cloudflare-migration.md); this page records the facts that apply to us and the order of the steps.

## Facts checked on 28 November

- `etnos.space` is registered at **Namecheap**. Its nameservers are Cloudflare's (`cartman` and `molly`), which serve the zone in the old account. The domain does not need a registrar transfer. It moves by adding the zone to the new account and changing the two nameservers at Namecheap ([Cloudflare: move a domain between accounts](https://developers.cloudflare.com/fundamentals/manage-domains/move-domain/)).
- The new account gets its own nameserver pair, which can differ from the old pair. While the zone is *Pending* in the new account, it cannot proxy traffic. When Namecheap points at the new pair, the zone turns *Active* there, and the old zone shows *Moved Away* and is deleted after 7 days.
- DNSSEC must be off at Namecheap before the move.
- Cloudflare does not copy settings between accounts. The DNS records are exported from the old zone and imported into the new one, and certificates are issued again.
- The identity host holds 2 accounts: `uji-1.etnos.space` (test) and `giyaibo.etnos.space` (the owner's). Both DID documents name `etnos-identity-host.giyaibo.workers.dev`, which belongs to the old account.
- The node moves with its backup: Studio, *Pengaturan*, then the download, then `POST /v1/ops/restore` on the new Worker (runbook §1b).

## Order

1. **Finish and check everything on the old account first** (owner decision, 28 November).
2. **Move the identity host to `akun.etnos.space` on the old account** (runbook §6). This step repoints both DID documents to a name that we control, while the old host still holds the keys. After it, the workers.dev name no longer matters.
3. **Move the host accounts with an operator export and import (recommended, 28 November).** The host's `createAccount` takes no existing DID, so standard AT account migration into our host does not work today. Once the host answers on `akun.etnos.space`, the DID documents name that address, and the address moves with DNS. The accounts then move without any PLC change if the host's state moves with them. The work to build before cutover day:
   - `POST /admin/accounts/export` on the old host returns every account's state: repository, blobs list, password hash, passkeys, recovery code hash, handle and keys. The keys are re-wrapped under a one-time transfer key that is set as a secret on both hosts, and never under the old key-encryption key.
   - `POST /admin/accounts/import` on the new, empty host unwraps them with the transfer key, wraps them under its own key-encryption key, and refuses to run on a host that already holds accounts.
   - Blobs are copied from the old `etnos-identity-blobs` bucket to the new one.
   - Tests cover a round trip, a wrong transfer key and a non-empty host.

   The owner's escrow key stays as the fallback. With it, the owner can point a DID at new keys if the export fails.

   Built on 28 November (`packages/pds/src/host/transfer.ts` and `packages/pds/scripts/copy-identity-blobs.mjs`, with tests). The commands use placeholders only:

   ```bash
   # 1. The same one-time transfer key on both hosts (32 random bytes, base64url). Keep it only until step 5.
   node -e 'process.stdout.write(require("crypto").randomBytes(32).toString("base64url"))' > transfer.key
   npx wrangler secret put ACCOUNT_TRANSFER_KEY --config packages/pds/wrangler.host.jsonc < transfer.key   # old account
   CLOUDFLARE_ACCOUNT_ID=<new-account-id> CLOUDFLARE_API_TOKEN=<new-token> \
     npx wrangler secret put ACCOUNT_TRANSFER_KEY --config packages/pds/wrangler.host.jsonc < transfer.key # new account
   # 2. Export from the old host.
   curl -fsS -X POST https://akun.etnos.space/admin/accounts/export \
     -H "Authorization: Bearer <old-operator-token>" -o host-export.json.gz
   # 3. Copy the blobs (R2 API tokens from each account's dashboard).
   OLD_R2_ACCOUNT_ID=<old-account-id> OLD_R2_ACCESS_KEY_ID=<id> OLD_R2_SECRET_ACCESS_KEY=<secret> \
   NEW_R2_ACCOUNT_ID=<new-account-id> NEW_R2_ACCESS_KEY_ID=<id> NEW_R2_SECRET_ACCESS_KEY=<secret> \
     node packages/pds/scripts/copy-identity-blobs.mjs
   # 4. Import into the new host while it still answers on its workers.dev name.
   curl -fsS -X POST https://etnos-identity-host.<new-subdomain>.workers.dev/admin/accounts/import \
     -H "Authorization: Bearer <new-operator-token>" -H "content-type: application/gzip" --data-binary @host-export.json.gz
   # 5. Remove the transfer key from both hosts, and delete transfer.key and host-export.json.gz.
   npx wrangler secret delete ACCOUNT_TRANSFER_KEY --config packages/pds/wrangler.host.jsonc
   ```

   The import refuses, with nothing written, on a host that already holds accounts, a wrong transfer key, another format version, or a file that is not an export. It writes the directory last, so an import that stops halfway can be run again. People sign in once more afterwards, because sessions are not copied.

   **Service bindings.** The new account has no news engine Worker (`WATCH_NEWS`) and, until the owner deploys it, no resident Worker (`RESIDENT_PI`), and `wrangler deploy` fails on a binding to a missing Worker. Set the repository variable `ETNOS_OMIT_SERVICES` to `WATCH_NEWS,RESIDENT_PI` for the new account; news is then read from the public site.
4. **Cutover day, in one window of about an hour**, announced to the alpha group:
   - Set the GitHub secrets `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` to the new account (the owner does this in GitHub settings, never in chat). Set the repository secrets `ETNOS_LINK_KEY`, `ETNOS_VAPID_PUBLIC_KEY` and `ETNOS_VAPID_PRIVATE_KEY` if we want them stable.
   - Create `etnos-node-backups` and `etnos-identity-blobs` in the new account and run the deploy workflow. Both Workers then answer on the new workers.dev name.
   - Download the node backup from the old Studio, and restore it into the new node.
   - Move the host accounts as decided in step 3.
   - Add `etnos.space` to the new account, import the exported DNS records, turn DNSSEC off at Namecheap, and change the nameservers there.
   - When the zone is *Active*, the deploy workflow attaches `etnos.space`, `*.etnos.space/*` and `akun.etnos.space/*`.
   - Run runbook §5 checks, then sign in as the operator and as a test account.
5. **Writes during the window are not carried over.** Some readers reach the old account until their resolvers see the new nameservers. The window is announced so that nobody posts during it.

## What the owner provides

- The new account ID and API token, as GitHub secrets on the cutover day.
- Namecheap access for the nameserver change and DNSSEC.
- The escrow key, if step 3 uses it.
